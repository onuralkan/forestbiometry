## 3. Data flow (honest statement)
- **Tools:** The user's file is read in the browser (`File.arrayBuffer`) and **is not sent to the server**. All calculations are done in the browser. The server only serves the page and the JS files.
  If a tool later needs server-side calculation, the data flow is stated clearly on that tool's page and here; the phrase "does not leave the device" is not used.
- **Accounts: AI interpretation and saved results (21–22 Nov 2026, user decisions; the only exception, PLATFORM_PLAN P1).** Data policy: raw data (tables, files, a run record's embedded input data) are never sent to or kept on the server; analysis results may be kept for their owner. Sign in with ORCID only (`auth/orcid.php`, scope /authenticate), accounts approved by the administrator; the top bar shows "Sign in" or an account menu (name, ORCID, use this month; My interpretations, Saved results, Account settings, Accounts for the administrator, Privacy, Sign out).
  - *Interpretation:* a tool may offer an "AI interpretation" card (`assets/lab/core/interpret.js`; pilot: Model Evaluation). Only on the button, the summary of that one result (the run-record payload: settings and result tables, no rows or input files) goes to `api/interpret.php`, which forwards it to Anthropic's Messages API (model in the private config, default `claude-opus-5-5`). 30 interpretations per account per month (UTC), at most 3 a minute, no daily limit by default (all three and personal limits set in `administration.php`); a failed call gives the interpretation back. Every interpretation is saved to the account automatically with its summary and the summary's key (`keyOf`), unless the account's storage is full. A tool joins by adding its id and a description of its result object to `FB_TOOLS` (`inc/ai-tools.php`, read by the API and the administration panel) and calling `mountInterpret()` on its result view; the panel then shows an on/off switch for it.
  - *Saved results:* "Save to my account" (`core/record-ui.js`, next to every tool's "Run record (JSON)" button, shown only for approved accounts via `body[data-acct]`) presses the JSON button in save mode and posts the run record, always without input data, to `api/library.php`; the server refuses `inputs[].data` (422 raw-data). Tree-level result tables of some tools (Stand Structure: d and species per tree; Stem Taper: D and H per tree) repeat measured values; they are accepted with the record, and the privacy notice says so (22 Nov 2026, user decision: disclose rather than strip, so the saved record stays identical to the download and its seal holds). A saved result links to the interpretations of the same summary key. Limits (private config): 200 results, 20 MB per account, 2 MB per record, 10 saves a minute. `account.php` tabs: Profile (state with reason and end of a block, use this month and today, storage, the administrator's announcement, export of everything as JSON, delete saved items, delete account), Interpretations, Saved results (a result is drawn again from its record by `assets/lab/library/` — tools with their own view in `VIEWS`, so far Model Evaluation, Diameter Distribution, Relative Ranking, Plot & Stand Metrics, Height–Diameter, Growth Function, Site Index, Stem Taper, Volume Equations, Biomass & Carbon and Stand Structure (`<tool>/view.js`: tables and charts computable from the saved numbers; a view may return `{ html, rest }` to leave parts to the generic view), every other tool the generic view of the record's tables; the seal is checked; title and note editable; the record is stored byte for byte as the browser sent it, so the seal holds), and for the administrator a link to the **administration panel** `administration.php` (22 Nov 2026, plan `docs/ADMIN_PLAN.md`): Overview (accounts by state, waiting accounts with approve/reject, use today and this month, storage, backup age, retention), Accounts (search, state filter, order, CSV), an account page (state approved / waiting / not approved / blocked with a reason shown to the user and an optional end date, lifted automatically; personal monthly and daily quota, extra interpretations this month, reset of this month's or today's use, private note, use by month and day, storage counts only, deletion with the ORCID iD typed, the account's audit entries), Settings (default monthly / daily / per-minute limits, sign-up mode approval / automatic / closed, service on/off with a message, announcement; stored in the `settings` table, overriding `config.php`) the Audit log (every change and the automatic ones, 24 months, CSV) and **Usage** (stage 2, 22 Nov 2026): every interpretation request in the `calls` table (time, account, tool, outcome ok / upstream / refusal / empty / off / cap / rate / daily / quota, tokens from the API's `usage`, duration, model; never the summary or the text; 13 months; on account deletion the lines stay without the ORCID iD), this month's outcomes, the last 30 days, accounts and tools this month, recent problems, CSV; estimated cost only from prices the administrator enters (none built in); **site-wide monthly caps** of interpretations and of tokens (0 = none; `cap`, 503, for everyone); the accounts close to the 24-month deletion and a manual run of the retention rule. Stage 3 (22 Nov 2026): on the Overview, switches of the interpretation for the whole service and for each tool of `FB_TOOLS` (setting `tools_off`; API `tool-off`, 503; the card says it is paused; e.g. when the API balance runs out), and on the Accounts list one state for several selected accounts (never the administrator's own); all audited. The panel never shows the content of saved results or interpretations. Every query of the account pages is limited to the signed-in owner.
  - *Literature box (23 Nov 2026, user decision):* on every tool page, for the administrator only, a closed box "Literature from Scopus" (`inc/site.php` `site_bottom`, `core/literature.js`) lists the most recent or most cited publications for the tool's search query from the Scopus Search API through `api/literature.php` (`inc/literature.php`; 404 for everyone else). The Elsevier key (`elsevier_key`, optional `elsevier_insttoken`) is only in the private `config.php`; no box without it. Only the tool's query goes to Elsevier, never anything of a visitor; nothing is fetched until the box is opened; lists are cached 24 h in the private database (`lit_cache`); the administrator can edit each tool's query in the box (`lit_queries`, audited; default queries in `FB_LIT_DEFAULT`). Shown with the Scopus attribution, for the administrator's own use. Tests: `tests/account/e2e.mjs` §5d (`elsevier_mock`).
  - *Retention and backup:* items stay until the owner deletes them; an account not signed in for 24 months is deleted with everything it keeps (`fb_purge`, daily). The host's cPanel backup does not cover the private folder: a cron job runs `php <web root>/inc/backup.php` nightly (consistent copy with `VACUUM INTO`, gzip, `<private>/backups/fb-YYYY-MM-DD.sqlite.gz`, newest 30 kept; also runs the retention rule); the administrator can download the newest copy from the Accounts tab.
  - *Storage:* SQLite in a private folder outside the web root (`FB_PRIVATE`, else `<parent of the document root>/forestbiometry-private/`: `config.php` from `scripts/private-config.example.php`, `fb.sqlite`, `backups/`), never in the repository and never touched by the deploy. Without the config every page works as before (no account link, no card, no save button; `api/interpret.php` answers `configured: false`). A session cookie exists only after signing in. Privacy notice `privacy.php`. Tests: `tests/account/e2e.mjs` (own PHP server with a mock config: ORCID and Claude mocked).
- **No other data flow on the site:** there are no other accounts or forms and no external resources (CDN, font service, analytics code). Apart from the host's usual access logs and the accounts (with what their owners save), the server records nothing.
- **Module loading and caching (12 Nov 2026; bundling 16 Nov 2026):** the sources are ES modules under `assets/lab/` (the tests import them directly). **On the server each page loads a single file:** `scripts/bundle.mjs` (parses with acorn, its only external dependency) bundles each tool page's entry module and the citation dialog (`core/cite-ui.js`) into a single ES module and writes it to `assets/build/<tool>/ui.js`, writes the Workers to their relative locations in the source (`assets/build/dist/boot-worker.js` …), and writes the citation dialog alone to `assets/build/core/cite-ui.js`. The output is deterministic and **is committed**; CI checks with `node scripts/bundle.mjs --check` that it matches the sources, otherwise the release stops. Rationale: the host's bot protection (openresty, "One moment, please...") returned HTML instead of JS to the 59 concurrent module requests of the diameter distribution page, and the tool stayed empty; with bundling, 3 requests per page. `site_bundles()`: bundled files on the server; on the PHP built-in server (development, tests) the sources, unless `FB_BUNDLE=1` is given. The bundler's limits (no default export, no top-level await, no cycle with named imports; a cycle with namespace imports is accepted) are written at the top of the script; if they are exceeded, the build stops. In source mode: `inc/site.php` extracts each page's module chain from relative `import` lines (`site_module_graph`), writes an import map giving each module its file time as a version tag, and `modulepreload` links (`site_modules_html`); the `?v=` value of page scripts and of `lab.css` is also the file time (not incremented by hand). `.htaccess`: JS/CSS carrying `?v=` stays in the cache for a year, untagged ones (Web Workers and their imports) are revalidated with ETag every time. A new module enters the chain only if it is linked with relative `import`/`export … from`; Workers opened with `new URL(…, import.meta.url)` stay untagged.
- **Browser storage:** Tool sessions and approved data are in IndexedDB (every tool has a delete button); the theme in `localStorage`; the language in a cookie. IndexedDB is bound to the domain: old onuralkan.com.tr sessions do not carry over to the new domain.

## 4. Data contract (tree table)
After the column mapping screen, all tools convert the imported table into these **canonical fields**. Internal units are fixed; conversion is shown explicitly.

| Field | Type | Internal unit | Note |
|---|---|---|---|
| `row` | integer | – | Row number in the source file (header = 1). All errors and warnings are reported with this number |
| `plot_id` | text | – | Plot ID |
| `tree_id` | text | – | Tree ID within the plot |
| `period` | text/number | – | Measurement period or year |
| `species` | text | – | The user's species code; the site **does not impose** its own code list, the user may supply a mapping table |
| `dbh` | number | cm | DBH (1.30 m). mm/m inputs are converted on the mapping screen |
| `height` | number | m | Total height. `null` if not measured |
| `plot_area` | number | m² | At row or plot level; converted if entered in ha |
| `status` | text | – | Live, dead, cut, etc. (user-defined values) |
| `x`, `y` | number | m | Optional coordinates |
| `extra.*` | – | – | Unmapped columns are preserved and written back on export |

Additional fields (Module 1): `stem_id` (text, multi-stemmed trees), `stratum` (text, stratum). IDs (`plot_id`, `tree_id`, `stem_id`) are kept **as text**: "001" and "1" are different, whitespace is not trimmed automatically (warning + suggestion). In XLSX the ID is the cell's displayed text; date-formatted cells are converted to ISO text (YYYY-MM-DD).

Rules: A missing value is `null`, **never 0**. Predicted values (for example height) are marked with a flag separate from measured ones. The decimal separator may be a comma or a point; it is converted to a number internally.

## 4b. Data transfer between tools (`forest-dataset/1`)
Data approved in the Data Checker is stored in the browser's IndexedDB store (`forestbiometry` / `kv`; its name was `onuralkan-lab` until 9 Nov 2026) under the key **`dataset:approved`** and can be downloaded as JSON. Later tools read this object; it does not go to the server. The layers are separate:
- **Raw data:** The user's file; never changed (`sources` in the session).
- **Approved data:** Measurements with corrections applied, exclusions removed, converted to internal units (`plots`, `trees`).
- **Derived values:** Under `derived`, separate from the measured data.
```
{ schema: 'forest-dataset/1', created: ISO, tool: {id, version},
  units: {dbh:'cm', height:'m', plot_area:'m2', x:'m', y:'m'},
  source: {trees:{name,kind,meta,records}, plots:{…}|null, mapping:{trees:{field:header}, plots:{…}},
           settings:{decimal, units (source units), limits}, lang},
  plots: [{plot_id, plot_area, stratum, area_source:'plots'|'trees'|'plots+trees', n_records}],
  trees: [{row, plot_id, tree_id, stem_id, period, species, dbh, height, status, stratum, x, y, extra:{header:text}}],
  derived: {note, trees:[{row, basal_area_m2}], plots:[{plot_id, expansion_factor}]},
  warnings: [{code, table, row, plot, field, accepted: reason|null}],
  excluded: [source row no], changelog: [{seq, time, action, table, row, field, column, old, new, reason, issue}] }
```
Empty plots appear in `plots` with `n_records: 0`. Optional package field `species_names: {code: full name}` (Data Checker 1.3.0, 21 Nov 2026): the user's names for the species codes that occur; absent without a species table; tools that do not use it are not affected. Optional tree field `age` (years; mapped by the Data Checker (12 Nov 2026); the direct table upload of the Plot & Stand Metrics tool also fills it). Optional tree field `height_source: 'measured'|'estimated'` (if absent, it counts as measured); consuming tools keep estimated heights separate. The first version of Module 5 writes predictions to a separate column only on export; writing to the approved data package (with a new version number) does not exist yet. Approval is given only when the **error count is 0**; open warnings remain in `warnings`. If the schema changes, the version number increases (`forest-dataset/2`) and reading tools reject or convert the old version.

**Transfer of derived values between tools (`forest-derived/1`; BC03, 17 Nov 2026, user decision: separate record, the package does not change):** tree values that a tool computes for the approved package are not written into the package (the package fingerprint and the DI-03 rule are preserved); they are kept as a separate record in browser storage under the key **`derived:<kind>:<package SHA-256>`**. `forest-dataset/1` did not change; tools that do not recognise this record are not affected. The first kind is `stem-volume` (Stem Section Volume writes it, Biomass and Carbon reads it):
```
{ schema: 'forest-derived/1', kind: 'stem-volume', created, tool: {id, version},
  dataset: {schema: 'forest-dataset/1', sha256, trees}, units: {volume: 'm3'},
  settings: {method, layout, top, includeStump, dTop, combine, barkDefault, thresholds},
  trees: [{row, plot_id, tree_id, period, status, v_ob, v_ib, label}],
  unmatched: [{plot_id, tree_id, period}], ambiguous: [{plot_id, tree_id, period, rows}] }
```
The reader (`core/derived.js` `readDerived`) converts every version in the version table to the current form and rejects an unknown version; if the fingerprint does not match that of the package in use, the record is not used. If the form changes, `forest-derived/2` and a converter is added to the reader.

**Inventory Data Manager (DI-03, 16 Nov 2026, user decision: multiple packages + active package, only metadata is edited):** each approved package is also kept as a project under the key `project:<id>`: `{ schema: 'forest-project/1', id, name, description, location, year, notes, origin: 'checker'|'import'|'legacy'|'copy', added, modified, sha256 (the package's canonical SHA-256, METHODS §20), dataset }`; `project:active` is the ID of the active project and **the active package is written to `dataset:approved`**, so the tools read the active package without change. The Data Checker calls `registerApproved()` on approval (a package with the same fingerprint is not added a second time); a pre-DI-03 `dataset:approved` is adopted as "earlier approval" when the manager is first opened. Package content is not changed in the manager (corrections are made in the Checker, with the log). Backup: `{ schema: 'forest-project-library/1', created, projects }`. "Deactivate" in the tool directory deletes only `project:active` and `dataset:approved`. Code: `assets/lab/core/projects.js`, page `data-manager.php` (`assets/lab/projects/`).

The session (`session:veri-denetcisi`) is kept in the same store; changing the language reloads the page and the session comes back.

**Tool-to-tool hand-off of a table (`handoff:<page>`):** a tool may put a one-off table for another page under the store key `handoff:<target page id>`; the target reads it once at start and deletes it. Used by Volume Equations and Nonlinear Regression → Model Evaluation (`{name, text (TSV), obs, models, role}`) and, since 21 Nov 2026, Height–Diameter Modelling → Nonlinear Regression / Mixed-Effects Models (`{schema: 'hd-handoff/1', name, text (TSV: plot?, species?, d_cm, h_m), y, d, group, units, bh, tool, created}`). The source data and packages are never changed.

## 4c. Run record (`run-record/1`; DI-07, 16 Nov 2026)
The tools' result JSON is written in a shared envelope (`assets/lab/core/record.js`, page side `core/record-ui.js`). The tool's old JSON fields **stay unchanged at the top level** (old readers are not affected); reserved fields are added:
```
{ format: 'run-record/1',
  tool: { id, version, ids: [catalog IDs], page },
  build: { commit: deployed git commit | null (development), site: SITE_BASE },
  created: ISO, lang: 'tr'|'en',
  inputs: [{ role, kind: 'file'|'paste'|'dataset'|'table', name, bytes, sha256, format?, encoding?, delimiter?, header?, sheet?,
             schema?, trees?, data?: { encoding: 'base64'|'utf-8'|'json', value } }],
  …the tool's own fields (settings, results, fits, units…),
  integrity: { algorithm: 'SHA-256', canonicalization: 'RFC 8785 (JCS)', value } }
```
Fingerprint and seal definitions: METHODS §20. `data` is written only when the user ticks "Include the input data in the record" (one shared choice per page, `localStorage` `recEmbed`; off by default). The commit is read from `deploy-commit.txt`, written on the server by the upload job (`site_commit()`, `#cite-data`); the file is closed to outside access and does not enter the repository. Data formats (approved data package `forest-dataset/1`, coefficient sets `model-coef/1`, library backup, Diameter Distribution stand model) are not records; they stay with their own schemas. The Record Verifier (`record-verifier.php`) checks the seal, the tool version and the fingerprints of the inputs in the browser. If the format changes, `run-record/2`.

## 5. Shared rules (every module)
1. In one round only the requested module is implemented; completed modules are not rewritten.
2. Interface, help, validation messages, chart labels and downloaded reports in TR/EN.
   Note (21 Nov 2026): English only; the Turkish code was removed in one step (stage 2). Text above about Turkish is history.
3. Calculation (`calc.js`) is separate from the interface (`ui.js`). Formulas, units, assumptions and sources are written in METHODS.md.
4. Data, equations, coefficients, sources, significance or uncertainty values are **not fabricated**. **The user enters** the coefficients of species/region equations; the site shows the equation form, and outputs carry the note "produced with user coefficients".
5. Every scientific calculation is tested against an independent reference (SciPy, R or a hand-verifiable example); the test is saved under `tests/`.
6. Calculations are done in the browser (see §3).
7. No non-working buttons, random results or placeholders that look finished. Sample data buttons state clearly that the data are a sample.
8. Existing content is preserved. A push to `main` is a release to production (automatic upload once the server details are filled in); tests are run before the push.
9. Routine technical decisions are made and written here; questions are asked only for gaps that block the work.
